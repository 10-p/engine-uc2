## What the reading phase established (sources named; "verified" = I read the code, nothing more)

### The driver as it is (`Source/UC2GLDrv`, 14.6k lines)

- Every GL call goes through a table of function pointers that are **static members of the device class**
  (`UC2GLFuncs.h`, about 120 entry points), filled by `FindProcs` from one lookup function. Nothing in the
  driver calls a `gl*` symbol directly, and the GL headers are included without prototypes. So which library
  the table points into is a run-time fact, not a compile-time one.
- Vertex data: buffer objects only (`glBindBuffer` + offsets) for every engine stream and index buffer. The
  two exceptions are the full-screen quads of the present pass and of the post-process copies, which pass a
  client-side array (WebGL has none).
- Fixed-function materials (M5): `GL_COMBINE` with three sources, `GL_MODULATE_ADD_ATI`
  (`ATI_texture_env_combine3`), texgen (eye linear, normal map, reflection map), texture matrices, lights,
  linear fog, colour material, secondary colour + colour sum, alpha test, polygon mode, polygon offset,
  `GL_TEXTURE_LOD_BIAS` through `glTexEnvf`. No clip planes, no points/lines state, no occlusion queries
  (answered "visible" in software), no display lists, no immediate mode.
- Programs (M6/M7): vertex shaders composed in C++ (`BuildVertexShaderSource`), fragment bodies generated by
  `tools/psh2glsl.py`; generic attributes 0..7; header `#version 120` prepended at compile time. Three copy
  programs + the present program likewise. The depth copy writes `gl_FragDepth`.
- Framebuffers: main FBO = RGBA8 texture + **depth-stencil texture** (sampled by the depth-encode and
  depth-copy passes); render targets = RGBA8 texture + own D24S8 renderbuffer or the main depth-stencil
  texture borrowed.
- Textures: DXT1/3/5 uploaded compressed when S3TC is there (else decoded by the engine's own decoder),
  `GL_BGRA` uploads for RGBA8, `GL_LUMINANCE`, `GL_ALPHA`, `GL_UNSIGNED_SHORT_5_6_5`; **mip chains stop
  before 1x1** (the engine clamps the number of levels to log2 of the *smaller* side) and
  `GL_TEXTURE_MAX_LEVEL` says so, set after the uploads.
- Read-back: `glReadPixels(GL_BGRA)` for screenshots, the self-test, `GLTEXELS`, and the dynamic gamma's
  16x16 luminance target every 0.05 s.
- The binding header was prepared for a compile-time choice (`UC2GL_BINDING_GL4ES` -> `#error`); the only
  place that used it was the present shader's version line.

### The template (engine-ut2004, read-only)

- gl4es: `FetchContent` of `https://github.com/10-p/gl4es.git`, ref `fix/cubemap-bind-active-unit` (unpinned
  branch; at the time of reading `98441ed`), options `NOX11 NOEGL STATICLIB DEFAULT_ES=2
  NO_INIT_CONSTRUCTOR`, archive output redirected into the build directory, `-O2` forced for it in the
  `-O0` web build (one of its functions otherwise exceeds V8's limit of locals after Asyncify).
- One binary carries the desktop driver and the GL4ES driver; they are two mirrored source directories
  there ("cannot coexist in one translation unit": each includes a different `GL/gl.h`, both PRIVATE).
  Symbols do not clash because the desktop driver links no GL library (pointer table from
  `SDL_GL_GetProcAddress`) and gl4es is compiled `-fvisibility=hidden`.
- Its GL4ES device: `set_getprocaddress(SDL_GL_GetProcAddress)` (web: `emscripten_webgl_get_proc_address`),
  `initialize_gl4es()`, then its own table from `gl4es_GetProcAddress`. Environment set before init:
  `LIBGL_ES=2`, `LIBGL_NOBANNER=1`, **`LIBGL_USEVBO=1`** (without it gl4es hands GLES client-side pointers
  and Emscripten's `FULL_ES2` emulation re-uploads the vertex range before every draw: measured there as
  15,322 WebGL calls and 585 MB per frame), **`LIBGL_BATCH=0`** (batching measured as a regression),
  `LIBGL_AVOID16BITS=1`, `LIBGL_NPOT=2`, `LIBGL_NOTEXRECT=1`, `LIBGL_SILENTSTUB=1`.
- Web context (its `SDL2Viewport.cpp`): under `PROXY_TO_PTHREAD` the canvas is transferred to the engine
  worker (`-sOFFSCREENCANVAS_SUPPORT -sOFFSCREENCANVASES_TO_PTHREAD=#canvas`); SDL's GL path is EGL, which
  Emscripten proxies to the main thread that no longer owns the canvas (Emscripten #24792), so the context
  is created directly: `emscripten_webgl_create_context("#canvas")` with **`majorVersion = 1`** (WebGL 1 =
  GLES2), `alpha 0`, `depth 1`, `stencil 0`, `explicitSwapControl = 1`, `renderViaOffscreenBackBuffer = 1`,
  made current on the worker; SDL keeps the window and the input (window created without
  `SDL_WINDOW_OPENGL`). Present = `emscripten_webgl_commit_frame()`. Link: `-sFULL_ES2=1`.
- The frame yield resumes from `setTimeout(0)` (already what `SDLLaunchWeb.cpp` does here).

### Traps already paid for (frontend `docs/migration/STATE.md`; `docs/10-porting-lessons.md` has none on GL)

1. `emscripten_webgl_commit_frame()` is a **stub** unless the link has `-sOFFSCREEN_FRAMEBUFFER`
   (2.43): presentation then depends on Chromium compositing when the worker's task ends, which works on
   Linux and gives about 1 frame/s on Windows. engine-unreal1/ut99 link the flag; engine-ut2004's
   CMakeLists does not have it yet. **We link it.**
2. With that flag Emscripten's emulated default framebuffer has a 16-bit depth buffer whatever the context
   attributes say (2.72; they patch the loader). Not our problem: the scene is drawn into our own FBO and
   the default framebuffer only receives the present pass (context created without depth and stencil).
3. `-pthread` must be a compile option for every object including gl4es (2.13.2). Here
   `cmake/UC2Web.cmake`... to be checked at G3 (the web build already compiles everything with it).
4. Extension queries must come from the context that renders (SDL owns no context on the web), and WebGL
   names differ: `WEBGL_compressed_texture_s3tc`, `WEBGL_depth_texture`, no `GL_` prefix (2.19).
5. A fix right on desktop GL can be fatal on WebGL: `GL_TEXTURE_GEN_Q` does not exist in GLES and gl4es
   (2.34: the web rendered black). Our `CommitTexCoords` calls `glDisable(GL_TEXTURE_GEN_Q)` and
   `glTexGenfv(GL_Q, ...)`: to be watched with `-glerrors` on the twin.
6. Client-side arrays through `FULL_ES2` are capped at 2 MB per draw and slow; we have none after the two
   quads are moved into a buffer.
7. The e2e harness **refuses software GL**: every launch has `--disable-software-rasterizer`, ANGLE over
   Vulkan, headless with `DISPLAY` unset (`packages/e2e/lib/gpu.js`, `playwright.config.js`); the GPU
   canary fails a test on SwiftShader/llvmpipe. This machine has a Quadro P620 visible to Vulkan
   (`vulkaninfo --summary`: `deviceName = Quadro P620`, driver NVIDIA 580), in use by the owner's desktop
   (607 of 2048 MiB at the time). So browser runs here can be on the real GPU; whether the headless
   Chromium actually binds it is a G4 observation.
8. gl4es compiled at `-O0` for the web makes the module uncompilable (see above).

### gl4es facts that decide the design (read in `build-native/_deps/gl4es-src` of the template, `98441ed`)

| Area | What gl4es does | Consequence |
|---|---|---|
| Shader sources (`shaderconv.c`) | Every source is converted: the `#version` line is removed, every `precision` statement is commented out, its own header is put first: `#version 100` + `precision highp float; precision highp int;` when the hardware reports fragment highp, else `mediump`. Support for higher GLSL versions is `#if 0`. `gl_FragDepth` gets `#extension GL_EXT_frag_depth` when the hardware has it; **otherwise the write is silently replaced by a dummy variable**. Overload helpers for `pow/max/min/clamp/mod` are inserted. | Our sources (already ES-1.00 subset) pass with the header swapped. The precision is gl4es's choice (highp when available), not ours. The depth copy must not rely on gl4es when `EXT_frag_depth` is missing: we must know ourselves and take a fallback. |
| ESSL version | ESSL 1.00 only. | WebGL 2 contexts accept ESSL 1.00 shaders but do **not** offer `EXT_frag_depth`, `OES_standard_derivatives`, `EXT_shader_texture_lod` to them, and WebGL 2 `texImage2D` rejects the unsized depth formats gl4es uses. **Decision 3: WebGL 1 context**, as the template. |
| Vertex attributes (`fpe.c`, `buffers.h`) | The conventional arrays ARE generic attribute slots (ARB numbering when the hardware has more than 8 attributes: vertex 0, normal 2, colour 3, secondary 4, fog 5, texcoords 8..). | Our programs use generic 0..7 and switch the conventional arrays off first and re-establish them for the next fixed-function draw, so the aliasing is survivable; `glVertexAttrib4f(2,...)` (our constant diffuse) overwrites gl4es's current normal: to watch. |
| Combiners | `ATI_texture_env_combine3` and `NV_texture_env_combine4` are implemented in its fixed-pipeline emulation and advertised. | The M5 material compiler's GL translation can stay as it is. |
| Alpha test | In its own generated shaders. A user program gets none. | Programs need the alpha test in the fragment shader on GLES (`UC2_ALPHATEST` exists in the generated bodies and is not used yet). |
| Extension detection (`hardext.c`) | By OpenGL ES names: `GL_OES_depth_texture`, `GL_OES_packed_depth_stencil`, `GL_OES_depth24`, `GL_EXT_texture_format_BGRA8888`, `GL_OES_element_index_uint`... | On WebGL 1 none of the three depth names exists (`WEBGL_depth_texture`; DEPTH_STENCIL renderbuffers are core): gl4es then gives a depth attachment a **16-bit renderbuffer and a separate stencil renderbuffer**, which WebGL 1 rejects as a combination. gl4es also issues DEPTH and STENCIL attachments separately for a depth-stencil texture, which WebGL 1 does not allow (one `DEPTH_STENCIL_ATTACHMENT`). So the depth-stencil side cannot go through gl4es on the web. |
| DXT (`texture_compressed.c`) | Always decompressed in software to RGBA8 (with `LIBGL_AVOID16BITS=1`); it never passes S3TC to the hardware. Mip levels are uploaded. | Works, costs 4-8x texture memory and load time. Passing compressed data around gl4es where the hardware has S3TC is a G5 item. |
| `GL_TEXTURE_MAX_LEVEL` | Remembered; used to **generate** the missing smaller levels at the moment the level equal to max level is uploaded (uncompressed path). GLES2/WebGL 1 have no max level. | The driver sets it after the uploads: on GLES every texture whose chain stops before 1x1 (all non-square ones) would be incomplete = black. The driver must complete chains itself on GLES. |
| NPOT | GLES2 = "limited": NPOT textures must be clamped and have no mips; gl4es forces that. | Render targets (NPOT) sampled with WRAP addressing get CLAMP. |
| BGRA | Converted in software when `EXT_texture_format_BGRA8888` is missing (WebGL). | Works; CPU cost per upload (G5). |
| Batching | `LIBGL_BATCH=0` as the template (its measurement). | - |

## Decisions (each with its evidence; "decided" does not mean "works": nothing has run yet)

### 1. One driver source, compiled ONCE; the binding is chosen at run time by the device class

Not "compiled twice" and not a mirrored directory. Because the pointer table is filled at run time and the
GL enums are the same numbers in every header, the same object code can talk to desktop GL or to gl4es.

- `UC2GLDrv.UC2GLRenderDevice` (unchanged name, default on the desktop): binds desktop GL through SDL.
- `UC2GL4ESDrv.UC2GL4ESRenderDevice`: a **subclass in a small package of its own** (`Source/UC2GL4ESDrv`, to
  be written next: the class, the gl4es glue, and on the web the WebGL context). It overrides the
  `Binding*` virtuals of the base class: context attributes (ES 2.0 profile), context creation, gl4es
  initialisation, the two lookups, swap, drawable size, "context alive". Selected by `-gl4es` or the ini.
- Everything else asks `UUC2GLRenderDevice::IsGLES` and the `Cap*` flags at run time. So a renderer fix
  reaches the web without anybody remembering to port it, and the native twin runs the identical code the
  browser runs except for `#ifdef __EMSCRIPTEN__` lines, of which there is so far exactly one kind (the
  depth-stencil attachment point, see 2).
- Two statically linked copies of the driver would have needed either a symbol-renaming header for about 40
  class names or a namespace around UObject macros; neither is needed now.
- Cost: the web build carries the desktop-only branches as dead code (a few hundred bytes), and the base
  class exists on the web although it cannot create a context there (`UC2GL_HAS_DESKTOP_BINDING 0`: it says
  so in the log and fails `SetRes`).

### 2. Through gl4es: everything, with one exception that goes around it

- THROUGH: all fixed-function state (its emulation is the reason gl4es is there), all our GLSL programs
  (handed over in the ES 1.00 subset so its converter only swaps the header), buffers, textures, colour
  attachments, clears, read-back. One state tracker: gl4es caches bindings and enables, so calling GLES
  behind its back for anything it tracks would desynchronise it.
- AROUND (the "raw" table, `Inc/UC2GLRawFuncs.h`: 14 entry points looked up in the library *under* the
  binding: `SDL_GL_GetProcAddress` natively, `emscripten_webgl_get_proc_address` on the web; for the desktop
  binding the same functions as the main table): **depth-stencil storage and its attachment**
  (`CreateDepthStencilTexture/Renderbuffer`, `AttachDepthStencil*`, `AttachMainDepthStencil` in
  `UC2GLRenderDevice.cpp`), for the reason in the table above, plus the hardware's own extension string and
  fragment precision (`DetectCapabilities`). Rules that keep gl4es consistent: the texture *name* comes from
  gl4es and the texture is later bound for sampling through gl4es; the raw texture binding that the storage
  call needs is restored to what `GL_TEXTURE_BINDING_2D` said before; renderbuffers are raw from creation
  to deletion (the driver has no others, and with this path gl4es never creates its own).
- The one line where twin and browser differ: OpenGL ES 2 proper has no `GL_DEPTH_STENCIL_ATTACHMENT` (the
  image goes on the depth and on the stencil point), WebGL 1 has only that one for a depth-stencil image.
  `#ifdef __EMSCRIPTEN__` inside `AttachDepthStencilTexture/Renderbuffer` and the renderbuffer format
  (`DEPTH_STENCIL` on WebGL, `DEPTH24_STENCIL8_OES` on ES 2).
- To be verified by running, each with a check: that gl4es is not confused by a texture whose storage it
  did not see (self-test `depth-color`), by attachments it did not see (`glCheckFramebufferStatus`, clears
  with depth and stencil), and that its `glBindFramebuffer` binds immediately (the raw attachment call
  relies on it).

### 3. WebGL 1

See the table: gl4es emits ESSL 1.00 only; ESSL 1.00 on WebGL 2 loses `EXT_frag_depth`; WebGL 2 rejects
gl4es's unsized depth formats. The template uses `majorVersion = 1`. WebGL 1 with `WEBGL_depth_texture`,
`EXT_frag_depth`, `OES_element_index_uint`, `WEBGL_compressed_texture_s3tc` gives everything the driver
uses; each of the four has (will have) a fallback and a mask switch.

### 5. Precision

gl4es writes `precision highp float` into both stages when the hardware reports fragment highp, and removes
ours. `DetectCapabilities` logs the hardware's fragment highp precision (raw `glGetShaderPrecisionFormat`)
so a mediump-only device is visible in the log; the depth math (24-bit value rebuilt from three bytes, the
depth copy) needs highp. What happens on a mediump-only device is not handled yet (listed as open).

### 6. Gamma

No hardware gamma anywhere: the present pass applies brightness/contrast/gamma and the dynamic ramp on every
binding already (M5/M7). Nothing to do for the web.

Facts found on the way:

- **Mesa answers an ES 2.0 request with an ES 3.2 context** (`GL_VERSION` of the raw library). So the twin's
  "GLES2" is the ES 2 API on a context that would also accept ES 3 calls: an ES-2-only restriction that the
  driver violates would not be caught here, only in the browser (WebGL 1 is strict). The driver's own
  capability flags come from the extension strings and are honest either way.
- **gl4es's wireframe emulation crashes with real buffer objects**: the first frame of the menu died with
  SIGSEGV inside Mesa, called from gl4es `draw_renderlist` <- `gl4es_glDrawRangeElements` <-
  `FOcclusionQueryManager::RenderQuery`. gl4es turns a draw into a "render list" when the polygon mode is
  `GL_LINE` (`should_intercept_render`), and that path hands GLES client pointers. Two changes, both in
  `UC2GLRenderInterface.cpp`:
  1. `BeginOcclusionQuery`/`EndOcclusionQuery` set a flag and `DrawPrimitive` draws nothing in between. The
     engine's query geometry is wireframe boxes with colour, depth and stencil writes off; without a real
     query (PC and here: answered "visible") those draws have no effect at all. Also saves the draws on the
     desktop (G5).
  2. On GLES `glPolygonMode` is never called; a pass with `FM_Wireframe` is drawn as a line list built from
     the triangle indices (`DrawWireframe`; the indices come from the engine's index buffer, or from a CPU
     copy of the last dynamic indices). **Not exercised yet by any content I have run** (the occlusion boxes
     were the only wireframe draw in the menu): status "written, never drawn".
- gl4es reports 16 texture image units; the driver uses 8 as on the desktop.
